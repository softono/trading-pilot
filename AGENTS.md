## Project Overview

A full-stack Next.js app — public frontend, admin panel, and API all live in one project. Auth is fully custom (no third-party auth library). Data layer is PostgreSQL via Drizzle ORM. No test runner is configured.

## Tech Stack

- **Framework**: Next.js (App Router, Route Handlers) + TypeScript
- **Database**: PostgreSQL + Drizzle ORM (`drizzle-orm` + `postgres` driver), drizzle-kit migrations
- **Validation**: Zod (single source of truth for server + client validation)
- **UI**: shadcn/ui + Tailwind CSS v4 (no `tailwind.config.js`), TanStack React Table + TanStack Query, `react-hot-toast`
- **Auth**: custom — `argon2` (passwords), `otplib` (TOTP), `@simplewebauthn` (passkeys), `openid-client` (Google OAuth)
- **Caching**: Redis (or in-memory `node-cache` fallback)
- **Dates**: Luxon

## Repository Structure

The codebase enforces a strict boundary: **no `"use client"` module may import from `src/server/`** (type or value). Server Components (`page.tsx` without `"use client"`) may freely import server services — they run on the server.

**Server-only:**

- `src/server/` — all backend concerns. Contains:
  - `config.ts` — server-only secrets (`DATABASE_URL`, etc.).
  - `lib/` — core server libraries (DB, cache, encryption, logger, mailer, filesystem, pagination, rate limiting, validator, date formatting).
  - `middleware/` — auth middleware (`withAdminAuth`, `withUserAuth`).
  - `models/` — Drizzle table definitions and row-type exports (`IUser`, `IBlog`, etc.).
  - `modules/` — backend-only module logic. Contains sub-folders per module (e.g., `auth/`, `admin/`, `blog/`, `note/`, `account/`) holding server services (e.g., `blog.service.ts`) and endpoint/server validators.
  - `utils/` — server utilities (authCookie, clientInfo, parseBody, response, permissionsService).

**Shared / Frontend Modules (client + server may import):**

- `src/modules/` — client-facing and shared concerns structured by module (e.g., `auth/`, `blog/`, `note/`, `page/`, `account/`). Contains:
  - `<module>.constants.ts` — shared constants (e.g., categories, roles, countries).
  - `<module>.types.ts` — client-facing DTO interfaces and wire shapes (with string dates).
  - `<module>.validator.ts` — shared zod schemas (domain validation).
  - Frontend page components or local helpers.
- `src/types/` — global shared/generic types (like `ApiResult`, `ApiResponse`).

**Client infrastructure & utilities:**

- `src/lib/` — infrastructure & third-party integrations (authClient, httpClient, Luxon date formatting, form errors, message/toast helpers, `cn` utility).
- `src/utils/` — pure helper functions with no external library dependencies (fileurl, ipinfo, permission, safeRedirect). Safe for both client and server to import.
- `src/config.ts` — client config (`NEXT_PUBLIC_*` vars, API URLs, app metadata).

## Architecture Overview

### Route layout

| Path                 | Purpose                                                          |
| -------------------- | ---------------------------------------------------------------- |
| `/`                  | Public user-facing frontend                                      |
| `/admin/*`           | Admin panel (separate auth, layout, context)                     |
| `/api/auth/*`        | Public auth routes (login, register, OAuth)                      |
| `/api/(user)/auth/*` | Authenticated auth routes (logout, session, 2FA setup, passkeys) |
| `/api/(user)/*`      | Authenticated user API routes                                    |
| `/api/admin/*`       | Admin panel API routes                                           |

A request flows: route handler → `withUserAuth`/`withAdminAuth` middleware (attaches `req.user`/`req.session`) → `validateData(schema, body)` → a service method (returns `ApiResult`) → `sendResult(result)`. See `docs/api.md` for the full contract and examples.

### Layouts

- `src/app/layout.tsx` — root layout; wraps with `Providers` (TanStack Query), theme scripts, and `Toaster`.
- `src/app/admin/layout.tsx` — admin layout (`AdminAuthContext`); `/admin/auth/*` gets `BlankLayout`, everything else gets `AuthenticatedLayout` behind `ProtectedRoute`.
- `src/app/(user)/layout.tsx` — public/authenticated layout (`AuthContext` + `MainLayout`).

## Database Overview

PostgreSQL via Drizzle ORM. `src/server/models/schema.ts` barrel-exports every table; individual model files live in `src/server/models/*.ts` with `I`-prefixed row types (`IUser`, `INote`, etc.) and `New*` insert types. Migrations are timestamped SQL files generated by drizzle-kit — **always generate, never hand-write**:

```bash
npm run db:generate -- --name=<migration_name>
npm run db:migrate
npm run db:seed
```

PK convention: `text` + `genId()` (`crypto.randomUUID()`) is reserved for the `user` table and directly auth-related tables (sessions, passkeys, two-factor, verification) — everywhere else, including low-volume content tables, use `serial` (plain incrementing `int`). See `docs/backend.md` for the full table list, the `users` model shape, and date/timezone/caching/config details.

## API Overview

Every route: `NextRequest` in, `ApiResult` out via `sendResult()`/`sendResultWithHeaders()`/`sendError()`. Body validated with `validateData(schema, body)` before touching a service. Modules follow standard REST CRUD: `route.ts` exports `GET` (list) and `POST` (create); `[id]/route.ts` exports `GET` (single), `PATCH` (update), `DELETE`; custom actions get their own `[id]/<action>/route.ts`. List endpoints are `GET` with `page`/`limit`/`sortField`/`sortDir`/`search` as plain query params and `filter` as base64-JSON (the one field with arbitrary nested shape) — response is `{ list, pagination }`, built with `Pagination.paginate()`. Full shapes, the pagination contract, and error-response examples: `docs/api.md`.

## Authentication Overview

Fully custom auth (no third-party library) — libraries in `src/server/lib/auth/`, business logic in `src/server/services/auth/`. Opaque random session tokens in an httpOnly cookie (`COOKIE_NAMES.SESSION`), Redis-cached with DB fallback. Email OTP is the default 2FA method; TOTP is an optional add-on. Roles are string-based (`SUPER_ADMIN`/`ADMIN`/`USER`) via `hasPermission()`. Frontend and admin panel share one session model but use **separate contexts** (`AuthContext` vs `AdminAuthContext`) — never mix their imports. Never hard-code cookie name strings — always use `COOKIE_NAMES.*`. Full session/2FA lifecycle, cookie table, and middleware detail: `docs/authentication.md`.

## Frontend Overview

shadcn/ui + Tailwind v4. Two server-driven list components in `src/components/tsgrid/`: `DataTable` (table, default choice, use for anything with row actions) and `TsGrid` (card grid, for visual/public content) — both take the same `columns`/`queryKey`/`fetcher` contract, detailed in `docs/tsgrid.md`. Create/edit forms: a dialog beside the list page for ≤3 fields, a separate `create`/`update/[id]` page for 4+ fields — full pattern in `docs/frontend.md`. Toasts via `src/lib/message.ts` helpers, never `toast(...)` directly. End-to-end steps for adding a whole new module: `docs/new_module.md`.

## Backend Overview

`src/server/lib/core/cache.ts` — Redis (`CACHE_DRIVER=redis` + `REDIS_URL`) or in-memory `node-cache` fallback; auth sessions/user lookups are cached 300s with explicit invalidation on mutation. All timestamps are `timestamptz` (stored UTC) — format them server-side with `dateTimeFormat(date, getClientTimezone(req))`, never send raw `Date` objects to the client. `src/server/config.ts` holds server-only secrets (`DATABASE_URL`, `SECRET_KEY`, `ENCRYPTION_KEY`); SMTP and Google OAuth credentials live in the `settings` DB table, not env vars. Full detail: `docs/backend.md`.

## AI Agent Instructions

Behavioral guidelines to reduce common LLM coding mistakes. **Tradeoff:** these bias toward caution over speed — for trivial tasks, use judgment.

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:

- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them — don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

When editing existing code improve adjacent code or comments.

When your changes create orphans:

- Remove imports/variables/functions that YOUR changes made unused.

The test: every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:

- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

## Coding Rules & Conventions

Do not keep legacy or backward-compatibility code. Prefer clean code.

### Types

- **API responses**: All API routes and API-facing service methods return `ApiResult` from `@/types/common`. Never create per-service response interfaces. `ApiResult` structure is frozen (`{ http_status, status, message, data }`) — never add top-level fields; nest extras (pagination, etc.) inside `data`.
- **No type aliases**: Never create aliases like `type UserRecord = IUser` or `type IUserDoc = UserRecord`. Use the canonical type directly (`IUser`, `ISession`, etc.). Import from the source (`@/server/models/User`, `@/server/models/Session`).
- **Reduce `any`**: Use proper types. `any` is acceptable only for: external input (`data: any` in service params), catch blocks (`error: any`), and `ApiResult`'s `data` field. For user rows use `IUser`, for session rows use `ISession`, etc.
- **Drizzle row types**: Use `I`-prefixed names as canonical (`IUser`, `IUserSession`, `ISetting`, etc.). Insert types use `New*` (`NewUser`).
- **No `name` field on users**: The `user` table has `first_name` and `last_name` (both `notNull`). There is no `name` column. When displaying a full name, compute it inline: `` `${user.first_name} ${user.last_name}`.trim() ``.

### Request handling

- **Services receive `NextRequest`**: Service methods that need request info accept `(req: NextRequest, body: any)` — never custom `{ headers, body, ip }` objects.
- **Timezone: pass `tz`, not `req`**: If a service only needs the client timezone (e.g. to call `dateTimeFormat`), compute `const tz = getClientTimezone(req)` in the route and pass `tz: string` into the service. Only pass the full `req` into a service when it genuinely needs more than the timezone (e.g. IP, headers, auth context).
- **Routes use `sendResult`**: When a service returns `ApiResult`, the route calls `return sendResult(result)`. When a route needs to set cookies (login, logout, 2FA), use `sendResultWithHeaders(result, headers)`. Guard clauses use `sendError(...)`.
- **Validation**: Always use `validateData()` from `@/server/lib/validator`, never call `schema.validate()` directly.

### Files & Images

- **User Image URL Resolution**: All user images (avatars, profiles) must be resolved to their fully qualified URLs on the server inside services using `getFileUrl` from `@/server/lib/file`.
- **Frontend Image URLs**: The frontend must not use `getFileUrl` for dynamic user images; it should render the resolved URL directly from the API. The frontend only uses `getFileUrl` from `@/utils/fileurl` for static assets (e.g., logo).

### Validators — naming conventions

Zod schemas are the **single source of truth** for server validation, wire types, and client form validation.

**Two-layer structure:**

1. **Domain validators** (`src/modules/<domain>/<domain>.validator.ts`) — shared primitive schemas and per-domain save/form schemas. Each domain (blog, page, email-template, user, contact, note) has one flat file. Route handlers and client forms both import from here. Examples: `blog.validator.ts` exports `blogSaveSchema`, `blogFormSchema`, `blogCategorySchema`; `user.validator.ts` exports `userStatusSchema`, `userRoleSchema`.

2. **Route-mirrored / Endpoint validators** (`src/server/modules/<route-group>/<page>.ts`) — per-endpoint schemas for auth and user admin routes only (where endpoints have genuinely different validation rules, e.g. `login` vs `admin/auth/login`, `create` vs `save`). These import shared primitives from domain validators (e.g. `userStatusSchema` from `@/modules/account/user.validator`) — never redefine magic strings inline.

**Rule: route validators must import from domain validators.** Never write `z.enum(["active","inactive"])` or `z.string()` for a field that has a shared schema. Use `userStatusSchema`, `userRoleSchema`, `blogCategorySchema`, etc.

**Naming:**

| Symbol          | Source                               | Used by                                |
| --------------- | ------------------------------------ | -------------------------------------- |
| `xxxSaveSchema` | `z.object({...})`                    | route handler (`validateData`)         |
| `XxxSaveInput`  | `z.input<typeof xxxSaveSchema>`      | request wrapper + service method param |
| `xxxFormSchema` | `xxxSaveSchema.omit().extend()` etc. | `zodResolver` in the page              |
| `XxxFormInput`  | `z.infer<typeof xxxFormSchema>`      | `useForm<XxxFormInput>`                |

- Wire type uses `z.input` (client may omit `.default()` fields); form type uses `z.infer`.
- **No aliases** — one canonical `XxxInput`, imported everywhere.
- Avoid `z.ZodIssueCode.custom` (deprecated) — use the string literal `"custom"` in `ctx.addIssue`.
- A `xxxFormSchema` that feeds `zodResolver` must not use `.default()` on form fields — it makes the input type `T | undefined` and breaks the resolver's type. Use a plain `z.boolean()`/`z.string()` instead.
- **Never define Zod schemas inline in components or route files.** All schemas live in `src/modules/` or `src/server/modules/`.

Body-less routes (GET, id-only POST) don't get a validator. `login`/`admin/auth/login` are separate files — never share schemas across auth endpoints.

### Shared types & constants

- **`src/types/`** — global shared types (like `ApiResult`, `Status`).
- **`src/modules/<domain>/<domain>.types.ts`** — per-domain client-facing interfaces (`User`, `Blog`, `Page`, `Note`, etc.) with string dates.
- **`src/modules/<domain>/<domain>.constants.ts`** — per-domain runtime constants (e.g., categories, roles). Domain constants may re-export (e.g. `USER_STATUS = STATUS` in `user.constants.ts` importing from `common.constants.ts`).
- **`src/server/constants/`** — server-only constants (`filepath`, `permissions`). Shared constants live in `src/modules/...` or global `src/constants/`, not here.

## Important Patterns

- **Route → service → response**: guard clause (`sendError`) → `validateData` → service call → `sendResult`. Don't skip `validateData` even for simple bodies.
- **List endpoints**: build a `.$dynamic()` query with your filters/search applied, hand it to `Pagination.paginate(query, body, sortMap, { defaultSort, mapRow })` — don't hand-roll limit/offset/count. See `docs/api.md`.
- **Dates**: format on the server with `dateTimeFormat(date, getClientTimezone(req))` before sending to the client; never ship raw `Date` objects. See `docs/backend.md`.
- **Server-error-to-form**: on a 422, read `error.data.errors` and call `applyServerErrors(form.setError, errors)` (`src/lib/formErrors.ts`) instead of showing a generic toast.
- **New module checklist**: model → schema barrel export → migration → validator → type → service → routes → list page → form. Full walkthrough: `docs/new_module.md`.

## Common Pitfalls

- Creating a per-service response interface instead of returning `ApiResult` — don't; extend `data` instead.
- Calling `schema.validate()` directly instead of `validateData()` — skips the standard error shape the client expects.
- Hardcoding a cookie name string instead of importing from `COOKIE_NAMES`.
- Importing `useAuth`/context from the wrong file (`AuthContext` vs `AdminAuthContext`) — they are not interchangeable.
- Writing `z.enum([...])` inline for a field that already has a shared domain schema (`userStatusSchema`, etc.).
- Sending an unformatted `Date` object in an API response instead of running it through `dateTimeFormat(date, getClientTimezone(req))`.
- Building a list endpoint without scoping the base query by `user_id` when the data is meant to be per-user — `Pagination.paginate()` does not do this for you.
- Using `getFileUrl` on the frontend for dynamic user images — only the server resolves those; the frontend renders the URL the API already returned.
- Picking a create/edit dialog for a form with 4+ fields, or a full page for a 2-field form — see the field-count rule in `docs/frontend.md`.
